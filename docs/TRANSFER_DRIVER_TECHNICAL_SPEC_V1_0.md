# Transfer Driver — техническое задание v1.0

**Статус:** УТВЕРЖДЕНО владельцем проекта  
**Дата утверждения:** 2026-11-06  
**Продукт:** Transfer Driver  
**Связанные системы:** Transfer Servis, uber-v3, Transfer Admin  
**Android:** Java + XML  
**Production:** основная линия разработки  
**STAGING:** только для необходимых изолированных тестов

> Это ТЗ фиксирует утверждённую продуктовую и архитектурную модель. На этапе утверждения сборка APK, merge и production deploy не выполнялись.

---

## 1. Архитектурная роль

Transfer Driver является водительским клиентом единой системы:

`Transfer Servis ↔ uber-v3 ↔ Transfer Driver ↔ Transfer Admin`

Backend `uber-v3` является авторитетным источником для:

- аккаунтов и ролей;
- подтверждённого телефона;
- регистрации и допуска водителя;
- документов и автомобилей;
- фотоконтроля;
- заказов и назначений;
- операционных состояний поездки;
- GPS;
- чатов;
- поддержки;
- административных решений;
- audit.

Критические права и статусы не определяются локально Android-клиентом.

---

## 2. Регистрация по номеру телефона

Регистрация водителя начинается самостоятельно в Transfer Driver.

Основной идентификатор водителя — подтверждённый номер мобильного телефона.

Номер хранится backend в нормализованном формате, например:

`+79991234567`

Один подтверждённый номер не может одновременно принадлежать двум активным водительским аккаунтам.

Подтверждение номера выполняется через **Firebase Phone Authentication**.

Сценарий:

`номер → Firebase Phone Auth → SMS-код → подтверждение → регистрационная анкета`

Подтверждение номера само по себе не даёт права выходить на линию. Статус аккаунта, роль Driver, допуск к работе и сессии определяет backend.

---

## 3. Первичная регистрация водителя

После подтверждения телефона водитель проходит мастер регистрации:

1. личные данные;
2. первичная проверка личности;
3. паспорт;
4. водительское удостоверение;
5. автомобиль;
6. СТС;
7. право использования автомобиля;
8. дополнительные документы;
9. полный фото-набор автомобиля;
10. отправка на административную проверку.

До одобрения администратором водитель не может выйти на линию.

---

## 4. Личные данные

Минимальный набор:

- ФИО;
- дата рождения;
- подтверждённый номер телефона;
- регион работы.

Дополнительные профильные поля могут добавляться в дальнейшем без изменения базовой модели допуска.

---

## 5. Паспорт и первичная идентификация

При регистрации обязательны:

- изображение первой страницы паспорта;
- страница регистрации по месту жительства;
- **селфи водителя с первой страницей паспорта в кадре**;
- отдельное эталонное селфи лица.

Назначение изображений разделяется:

- `passport_selfie` — подтверждение владения документом;
- `identity_reference_selfie` — эталон для последующих проверок лица.

Документы и эталонные материалы являются чувствительными данными и должны храниться с ограниченным доступом.

---

## 6. Проверка лица

Проверка личности водителя обязательна.

Первичная регистрация должна предусматривать:

- съёмку через приложение;
- liveness-проверку;
- сопоставление лица с эталоном;
- административное подтверждение.

Автоматическое сравнение является инструментом проверки, но не должно единолично принимать окончательное решение по спорным результатам.

---

## 7. Селфи-проверка перед каждой поездкой

Перед тем как водитель начинает движение к точке подачи, он обязан пройти селфи-фотоконтроль.

Проверка выполняется отдельно для каждого назначенного заказа и связывается минимум с:

- `driverId`;
- `orderId`;
- `vehicleId`;
- `verificationSessionId`;
- server timestamp.

Сценарий:

`заказ назначен → селфи → liveness → сравнение с эталоном → backend verified → "Ехать к пассажиру"`

Без успешной проверки переход в `en_route_to_pickup` запрещён.

Загрузка фото из галереи для этой проверки запрещается.

Состояния:

- `verified`;
- `retry_required`;
- `identity_mismatch`;
- `manual_review_required`.

При `identity_mismatch` начало поездки блокируется и создаётся security event для администратора.

Один mismatch не обязан автоматически навсегда блокировать аккаунт: спорный случай переводится на ручную проверку.

UX результата селфи-проверки утверждён по принципу предоставленного владельцем референса, но оформляется в фирменном стиле Transfer Servis.

---

## 8. Водительское удостоверение

Обязательны:

- лицевая сторона;
- обратная сторона.

Документ связывается с конкретным driver account.

Архитектура должна позволять позднее контролировать срок действия и категории.

---

## 9. Автомобили водителя

Один водитель может зарегистрировать несколько автомобилей.

Каждый автомобиль имеет собственный:

- `vehicleId`;
- VIN;
- госномер;
- марку;
- модель;
- цвет;
- статус;
- документы;
- фотографии;
- тариф/класс;
- состояние фотоконтроля;
- историю проверок.

**VIN обязателен при регистрации автомобиля.**

Каждый автомобиль проходит самостоятельную административную модерацию.

Одобрение одного автомобиля не означает автоматического одобрения остальных.

---

## 10. СТС и право использования

Для каждого автомобиля обязательны:

- лицевая сторона СТС;
- обратная сторона СТС.

Если автомобиль используется по договору аренды, загружается сам договор.

Документы связываются с конкретным `vehicleId`.

---

## 11. Дополнительные документы

Система должна предусматривать загрузку и проверку:

- ОСАГО;
- документа/разрешения, связанного с пассажирскими перевозками;
- диагностической карты;
- иных утверждённых позднее документов.

На этапе утверждения ТЗ эти документы рассматриваются как дополнительные проверяемые атрибуты, которые могут использоваться для повышения операционного приоритета водителя.

Точный юридически обязательный состав документов определяется отдельно перед production-реализацией соответствующей функции.

---

## 12. Фото автомобиля при регистрации

Обязательный полный набор:

1. вид слева;
2. вид спереди;
3. вид справа;
4. вид сзади;
5. открытый багажник;
6. салон заднего ряда;
7. салон переднего ряда.

Фото относятся к конкретному `vehicleId`.

Для контрольных процедур съёмка выполняется через приложение, а не простым выбором старого изображения из галереи.

---

## 13. Багажник

Фото открытого багажника обязательно.

Оно используется для оценки реальной полезной вместимости с учётом:

- газового баллона;
- дополнительного оборудования;
- сабвуфера;
- запасного колеса;
- иных постоянных элементов.

Для дальнейшего подбора заказа допускается классификация вместимости, например:

- `reduced`;
- `standard`;
- `large`.

Точная шкала определяется на этапе реализации.

---

## 14. Плановый фотоконтроль автомобиля

Каждый одобренный автомобиль проходит **полный фотоконтроль один раз в месяц**.

Backend хранит минимум:

- дату последней проверки;
- следующий срок;
- результат;
- идентификатор автомобиля;
- набор контрольных фото;
- администратора/сотрудника, подтвердившего результат.

После наступления срока предоставляется **24 часа** на прохождение проверки.

Состояние в этот период:

`grace_period`

Водитель получает предупреждение.

После истечения 24 часов без успешной проверки автомобиль:

- не может выйти на линию;
- не может получать новые назначения;
- остаётся заблокированным для новых заказов до успешного фотоконтроля.

Уже начатая поездка из-за наступления срока не прерывается.

---

## 15. Внеплановый фотоконтроль

При жалобе или инциденте администратор может немедленно назначить **полный внеплановый фотоконтроль**.

Причины могут включать:

- жалобу пассажира;
- повреждение;
- загрязнение;
- несоответствие автомобиля карточке;
- проблему с багажником;
- ДТП;
- иное изменение состояния автомобиля.

Администратор определяет режим:

- завершить текущую поездку, но запретить новые назначения;
- немедленно заблокировать автомобиль до проверки.

---

## 16. Несколько автомобилей и активный автомобиль

У водителя может быть несколько зарегистрированных и одобренных автомобилей, но одновременно на линии используется только один.

Перед выходом на линию водитель выбирает автомобиль.

Backend фиксирует:

`activeVehicleId`

После выхода на линию выбранный автомобиль считается рабочим.

Для самостоятельной смены автомобиля водитель должен:

1. выйти с линии;
2. выбрать другой одобренный автомобиль;
3. снова выйти на линию.

При активном заказе самостоятельная смена автомобиля запрещена.

---

## 17. Статус "На линии"

В нижней части главного экрана находится slider:

**Сдвиньте, чтобы выйти на линию**

После подтверждённого backend-перехода slider сворачивается в компактный элемент:

**Радар активен**

Состояния:

- `on_line`;
- `off_line`.

Перед `on_line` backend проверяет:

- account active;
- registration approved;
- identity verified;
- выбран `activeVehicleId`;
- автомобиль approved;
- фотоконтроль действующий либо в допустимом grace-period;
- автомобиль не suspended;
- обязательные проверки выполнены.

---

## 18. Назначение заказа

На утверждённом этапе водитель **не выбирает свободные заказы самостоятельно**.

Заказ назначает:

- OWNER/SUPERADMIN;
- либо уполномоченный DISPATCHER.

Назначение фиксируется как связка:

`orderId + driverId + vehicleId`

Таким образом заказ назначается не просто водителю, а конкретному водителю на конкретном автомобиле.

Самостоятельное принятие заказов может быть рассмотрено как будущий отдельный режим.

---

## 19. Рекомендательный подбор

Backend может ранжировать допустимые связки `driver + vehicle`, но не назначает заказ автоматически.

Сначала применяются жёсткие фильтры:

- водитель active и on_line;
- выбранный автомобиль approved;
- действующий фотоконтроль;
- соответствующий тариф/класс;
- достаточная вместимость;
- отсутствие конфликтующего активного заказа;
- отсутствие недопустимого временного конфликта с будущими заказами;
- выполнение обязательных пожеланий пассажира.

После фильтрации допустимо ранжирование по:

- ETA/расстоянию до подачи;
- соответствию пожеланиям;
- загрузке;
- будущим назначениям;
- подтверждённому расширенному комплекту документов;
- подтверждённой операционной надёжности.

Рейтинг должен быть объяснимым. OWNER видит причины рекомендации.

Жалоба влияет на рейтинг только после административного рассмотрения и подтверждения нарушения.

Финальное назначение выполняет человек.

---

## 20. Пожелания пассажира

Пожелания делятся на:

### Обязательные

Невыполнение исключает кандидата.

Примеры:

- количество пассажиров требует минивэн;
- обязательное детское кресло;
- большой багаж требует соответствующей вместимости.

### Предпочтительные

Не блокируют назначение, но могут влиять на ранжирование.

---

## 21. Состояния заказа и поездки

Основная state machine сохраняется:

`new → taken → in_progress → done`

Терминальный статус:

`canceled`

Операционные фазы хранятся отдельно:

- `assigned`;
- `en_route_to_pickup`;
- `arrived`;
- `in_trip`.

Переход к `en_route_to_pickup` разрешается только после успешной обязательной селфи-проверки.

---

## 22. Навигация

Первый этап использует внешнюю навигацию.

До начала поездки:

**Навигация к пассажиру**

`текущая позиция → pickup`

После начала поездки:

**Навигация до места назначения**

`текущая позиция → destination`

Приоритет:

- Яндекс Навигатор;
- Яндекс Карты.

Собственный turn-by-turn движок в первую версию не входит.

---

## 23. GPS

Transfer Driver публикует координаты только в разрешённом рабочем сценарии.

Требования:

- Foreground Service;
- Android permissions;
- timestamp;
- accuracy;
- server authorization;
- проверка assignment;
- stale detection;
- остановка передачи после завершения, отмены или переназначения.

GPS связывается с `driverId + activeVehicleId + assignment/order`.

---

## 24. Passenger ↔ Driver: обычный звонок

Обычный звонок выполняется через системный Android dialer.

Телефон пассажира доступен только назначенному водителю в разрешённом состоянии заказа.

Телефон водителя берётся из подтверждённого аккаунта.

---

## 25. Passenger ↔ Driver: чат

Чат привязан к `orderId`.

Переписка хранится на сервере **30 календарных дней**.

Участники видят только разрешённый чат собственного заказа.

Доступ к серверному архиву имеет только уполномоченный администратор.

Просмотр архива журналируется.

Участник не может бесследно изменить или физически удалить уже отправленное сообщение.

После установленного срока данные удаляются либо необратимо обезличиваются согласно backend-политике.

---

## 26. Passenger ↔ Driver: VoIP

Предусматривается WebRTC/VoIP:

- исходящие и входящие вызовы;
- signaling;
- STUN/TURN;
- FCM;
- background;
- microphone permission;
- timeout;
- завершение вызова.

Интернет-звонки **записываются по умолчанию**.

Запись связывается минимум с:

- `callId`;
- `orderId`;
- участниками;
- началом;
- окончанием;
- длительностью;
- защищённым audio resource.

Доступ к архиву имеет только уполномоченный администратор.

Прослушивание журналируется.

Перед production отдельно утверждаются уведомление/согласие участников, срок хранения, шифрование, удаление, резервирование и применимые юридические требования.

---

## 27. Driver ↔ Administrator: поддержка

В Transfer Driver создаётся раздел **Поддержка**.

Каналы:

- чат;
- обычный телефон;
- интернет-звонок.

Создаётся `supportCase`.

Категории включают:

- пассажир не вышел;
- задержка;
- автомобиль;
- маршрут;
- невозможность выполнения;
- переназначение;
- конфликт;
- другое.

Водитель не отменяет заказ самостоятельно: решение принимает уполномоченный администратор/диспетчер.

---

## 28. Transfer Admin

Создаётся отдельное полноценное административное приложение.

Базовые разделы:

- Главная;
- Заказы;
- Водители;
- Автомобили;
- Регистрации;
- Карта;
- Поддержка;
- Жалобы;
- Сотрудники;
- Архив чатов;
- Архив VoIP;
- Audit;
- Настройки.

---

## 29. OWNER / SUPERADMIN

Главная административная учётная запись принадлежит владельцу проекта.

OWNER имеет максимальный уровень контроля над:

- заказами;
- водителями;
- автомобилями;
- регистрациями;
- документами;
- фотоконтролем;
- назначениями;
- пассажирскими заявками;
- сотрудниками;
- поддержкой;
- архивами;
- GPS;
- жалобами;
- тарифами;
- правилами приоритета;
- настройками;
- permissions;
- audit.

Ни один другой пользователь не может изменить права OWNER, отключить его или удалить его audit.

OWNER может отменить или переопределить любое операционное решение диспетчера.

---

## 30. DISPATCHER

OWNER может создавать диспетчеров при росте количества заявок.

Основная задача DISPATCHER — операционная обработка заказов.

Права определяются granular permissions.

Примеры:

- `orders.read`;
- `orders.assign`;
- `orders.reassign`;
- `orders.cancel`;
- `drivers.read`;
- `vehicles.read`;
- `support.manage`;
- `gps.read`;
- `complaints.manage`.

Чувствительные разрешения выдаются отдельно:

- `drivers.verify_identity`;
- `drivers.verify_documents`;
- `vehicles.verify`;
- `documents.read_sensitive`;
- `chat_archive.read`;
- `calls.listen`;
- `staff.manage`;
- `settings.manage`;
- `audit.read`.

Обычный диспетчер не получает эти права автоматически.

Transfer Admin содержит очередь:

- Новые;
- На проверке;
- Требуют исправления;
- Одобренные;
- Отклонённые.

Администратор может отдельно проверить:

- личность;
- паспорт;
- ВУ;
- автомобиль;
- СТС;
- право использования;
- фотографии;
- дополнительные документы.

Проблемный отдельный элемент можно вернуть на повторную загрузку без сброса уже подтверждённых элементов.

Статусы регистрации:

- `draft`;
- `submitted`;
- `under_review`;
- `changes_required`;
- `approved`;

## 32. Статусы автомобиля

Минимально:

- `draft`;
- `pending_review`;
- `approved`;
- `photo_check_required`;
- `suspended`;
- `rejected`.

Критическое изменение VIN, госномера, СТС или права использования должно запускать повторную проверку соответствующей части карточки.

---

## 33. Переназначение

Переназначение требует причины и фиксируется в audit.

После переназначения старый водитель:

- теряет доступ к PII пассажира;
- теряет чат;
- прекращает GPS-сессию заказа;
- теряет права на заказ.

Новый водитель получает push и проходит новую обязательную селфи-проверку.

---

## 34. Audit

Обязательно журналируются критические действия, включая:

- регистрацию;
- подтверждение телефона;
- первичную identity verification;
- trip selfie verification;
- mismatch/manual review;
- просмотр чувствительных документов;
- одобрение/отклонение регистрации;
- регистрацию и изменение автомобиля;
- смену `activeVehicleId`;
- фотоконтроль;
- внеплановый фотоконтроль;
- блокировку;
- жалобу и решение;
- назначение;
- переназначение;
- отмену;
- изменение прав сотрудников;
- доступ к архиву чатов;
- прослушивание VoIP-записей.

Сотрудник не может удалить или изменить собственные audit-записи.

---

## 35. Безопасность данных

Паспорт, ВУ, СТС, договоры, селфи, фото и другие чувствительные файлы:

- не публикуются по открытым URL;
- не передаются через FCM;
- не пишутся в обычные application logs;
- доступны только авторизованному backend и разрешённым ролям;
- административный доступ к критическим данным журналируется.

FCM-сообщения не должны содержать PII, содержимое чатов, аудио или credentials.

---

## 36. Существующая staff-session архитектура

Текущая backend-модель access JWT + rotating refresh token сохраняется как базовая серверная сессионная архитектура.

Переход Driver на Firebase Phone Authentication должен быть реализован совместимо с существующим staff-auth контуром, а не простым переименованием `login` в `phone`.

Административная авторизация может сохранять текущую схему до отдельного утверждённого этапа миграции.

## 38. Зафиксированные ключевые решения

1. Регистрация Driver — по номеру телефона через Firebase Phone Authentication.
2. Подтверждение телефона не даёт автоматического допуска к работе.
3. Паспорт и селфи используются для первичной идентификации.
4. Эталонное селфи используется для дальнейшего сравнения.
5. Перед каждой поездкой обязательна отдельная селфи/liveness-проверка.
6. Без `verified` переход `en_route_to_pickup` запрещён.
7. VIN автомобиля обязателен.
8. Водитель может иметь несколько автомобилей.
9. Одновременно на линии используется только один выбранный автомобиль.
10. Заказ назначается на `driver + vehicle`.
11. Полный фотоконтроль автомобиля проводится раз в месяц.
12. После срока фотоконтроля действует grace-period 24 часа.
13. Жалоба может немедленно инициировать внеплановый полный фотоконтроль.
14. Slider "На линии" расположен внизу и после активации сворачивается в "Радар активен".
15. Заказ назначает только OWNER либо уполномоченный DISPATCHER.
16. Автоматическое назначение системой не допускается; система только рекомендует кандидатов.
17. OWNER/SUPERADMIN имеет абсолютный контроль.
18. OWNER может создавать DISPATCHER и выдавать granular permissions.
19. Чувствительные документы диспетчеру по умолчанию недоступны.
20. Passenger ↔ Driver chat хранится 30 дней.
21. Архив чата доступен только уполномоченному администратору.
22. Driver ↔ Admin работает как отдельная служба поддержки.
23. Passenger ↔ Driver VoIP записывается по умолчанию.
24. Архив VoIP доступен только уполномоченному администратору.
25. Первый этап навигации использует внешнее приложение.
26. Все критические действия проходят через audit.

## 39. Детали реализации, требующие отдельного технического утверждения

Эти пункты не меняют утверждённую архитектуру ТЗ, но должны быть закрыты перед соответствующим production-этапом:

- срок хранения trip-selfie;

- таймаут реакции водителя после назначения;
- конкретная модель turn-by-turn/GPS частоты и энергопотребления.
